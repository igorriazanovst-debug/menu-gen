# Dev как зеркало прода

Чтобы проверять исправления на dev-сервере и верить результату, на dev нужны
те же данные, что в проде. Здесь — как их туда перенести и почему перенос
устроен именно так.

| | prod | dev |
|---|---|---|
| Адрес | `https://menugen.ru` | `http://31.192.110.121:8081` |
| Каталог | `/opt/menugen` | `/opt/menugen` |
| Backend | docker, `127.0.0.1:8003` | docker, `127.0.0.1:8003` (nginx `:8081`) |
| Хост | выделенный | делится с чужим проектом (он держит 80/8080) |

## Чем dev обязан отличаться от прода

Совпадать должны код и данные. Каналы наружу — нет, и это не мелочь: в копии
прода лежат настоящие адреса, телефоны и привязки к чатам Telegram/Max. Тест
регистрации на таком контуре отправит письмо живому человеку, а celery-beat в
09:00 разошлёт настоящим людям уведомления о продуктах в холодильнике.

Поэтому на dev в `.env` обязателен хвост из `deploy/mirror/dev.env.sample`:
пометка контура `MENUGEN_ENV=dev`, почта в лог, оплата заглушкой, пустые токены
ботов. `restore_dev.sh` проверяет это **до** заливки и отказывается работать,
если что-то не так.

`MENUGEN_ENV` по умолчанию — `prod`. Сервер без явной пометки считается боевым:
забытая переменная не должна стоить данных.

## Разовая подготовка dev

```bash
ssh root@31.192.110.121
cd /opt/menugen
cat >> .env <<'ENV'
MENUGEN_ENV=dev
EMAIL_BACKEND=django.core.mail.backends.console.EmailBackend
PAYMENTS_STUB=True
YOOKASSA_SHOP_ID=
YOOKASSA_SECRET_KEY=
TELEGRAM_BOT_TOKEN=
MAX_BOT_TOKEN=
ENV
docker compose restart backend celery celery-beat
```

Проверить, что пометка доехала до приложения:

```bash
docker compose exec -T backend python -c "
from django.conf import settings; import django; django.setup()
print('MENUGEN_ENV =', settings.MENUGEN_ENV)" 2>/dev/null || \
docker compose exec -T backend python manage.py shell -c \
"from django.conf import settings; print('MENUGEN_ENV =', settings.MENUGEN_ENV)"
```

## Обновление зеркала (сколько угодно раз)

**1. Снимок на проде** — ничего не останавливает, прод продолжает работать:

```bash
ssh root@158.255.5.166
cd /opt/menugen && bash deploy/mirror/snapshot_prod.sh
```

Медиа копировать не нужно — картинки на dev берутся с прода через nginx
(см. «Картинки без копирования медиа»). Обычный режим:

```bash
WITH_MEDIA=0 bash deploy/mirror/snapshot_prod.sh
```

Полный снимок с медиа (полтора гигабайта, надолго) нужен, только если dev
должен пережить недоступность прода.

**2. Перенос** (команда печатается в конце снимка):

```bash
rsync -avz -e ssh /opt/menugen/backups/mirror/<TS>/ \
  root@31.192.110.121:/opt/menugen/backups/mirror/<TS>/
```

**3. Разворачивание на dev:**

```bash
ssh root@31.192.110.121
cd /opt/menugen && git pull
bash deploy/mirror/restore_dev.sh /opt/menugen/backups/mirror/<TS>
```

Скрипт по шагам: проверки контура → бэкап текущей базы dev → восстановление
дампа → медиа → миграции → обезличивание → относительные ссылки на медиа →
запуск и health-check. Откат к прежнему состоянию dev печатается в конце.

## Что делает обезличивание

`manage.py sanitize_dev --yes` (запускается внутри `restore_dev.sh`):

| Что | Как | Зачем |
|---|---|---|
| e-mail и имена обычных пользователей | `user<id>@dev.local`, «Пользователь N» | до живого человека нельзя дотянуться с dev |
| пароли обычных пользователей | делаются неиспользуемыми | украденный dev-дамп не даёт материала для подбора боевых паролей |
| сотрудники (`is_staff`) | не трогаются | под ними заходят в админку dev |
| телефоны и подтверждения телефона | стираются вместе с `chat_id` | бот с dev не напишет живому человеку |
| токены соцсетей | стираются | |
| `payment_id` у платежей | обнуляется | ни одно действие на dev не дотянется до настоящего платежа в кассе |
| периодические задачи | выключаются | рассылки с копии прода ушли бы настоящим адресатам |

Меню, рецепты, списки покупок, холодильник, подписки и семьи остаются как есть —
иначе воспроизводить баги не на чем.

Оставить себе рабочий вход под конкретным адресом:

```bash
KEEP_EMAILS="ты@example.com" bash deploy/mirror/restore_dev.sh /opt/menugen/backups/mirror/<TS>
```

## Картинки без копирования медиа

Медиа прода — полтора гигабайта, и гонять их ради каждого обновления зеркала
незачем. Вместо этого nginx на dev отдаёт `/media/` так: сначала спрашивает
свой бэкенд, и только если тот ответил 404 — идёт на прод.

Порядок именно такой, а не «сразу на прод»: фотографии, загруженные во время
теста на dev, лежат только в его volume, и запрос на прод вернул бы 404 —
выглядело бы это как потеря файла.

Настроено разово в `/etc/nginx/sites-enabled/menugen-debug`:

```nginx
location /media/ {
    proxy_pass http://127.0.0.1:8003;
    proxy_set_header Host $host;
    proxy_intercept_errors on;
    error_page 404 = @prod_media;
}

location @prod_media {
    # Без переменной в proxy_pass: имя резолвится при старте, отдельный
    # resolver не нужен. Исходный URI подставляется как есть.
    proxy_pass https://menugen.ru;
    proxy_ssl_server_name on;
    proxy_set_header Host menugen.ru;
}
```

**Резервные копии конфига держи вне `sites-enabled/`** — nginx подключает оттуда
всё по маске, и файл `menugen-debug.bak_…` становится вторым конфигом с тем же
`default_server`: `nginx -t` падает с «a duplicate default server». Копии
лежат в `/root/nginx-backups/`.

Проверка после правки — `nginx -t && systemctl reload nginx`, затем:

```bash
curl -s -o /dev/null -w '%{http_code} %{content_type} %{size_download}\n' \
  "http://127.0.0.1:8081/media/<любой существующий файл>"
```

Ожидается `200 image/jpeg` и ненулевой размер.

Следствие: картинки на dev зависят от доступности прода. Данные при этом никуда
не уходят — запрашиваются только файлы, которые прод и так отдаёт публично.

## Код

Зеркалирование данных ветку не переключает. Код на dev выкладывается как обычно:

```bash
cd /opt/menugen && git pull && docker compose exec -T backend python manage.py migrate && \
  docker compose restart backend celery
```

Если на dev код новее снимка, миграции в `restore_dev.sh` доедут сами — снимок
восстанавливается в схему прода, а `migrate` доводит её до состояния ветки.
Обратное неверно: **снимок прода нельзя развернуть на dev с более старым
кодом** — Django не умеет откатывать схему по дампу. Сначала обнови код.

## Чего это зеркало не даёт

- **Домена и HTTPS.** Ссылки из писем, возврат с оплаты и App Links завязаны на
  `menugen.ru`; на `http://IP:8081` они проверяются лишь частично. Полное
  совпадение потребует `dev.menugen.ru` с сертификатом, а порт 80 на том хосте
  занят чужим проектом.
- **Боевых интеграций.** Оплата на dev — заглушка, почта — в лог. Это
  сознательно: см. первый раздел.
- **Своих медиафайлов.** Картинки берутся с прода (см. выше); всё, что
  загружено на dev во время тестов, живёт только там и в снимки не попадает.
- **DEBUG.** На dev он `True` (так удобнее ловить ошибки), в проде `False`.
  Разница видна в поведении статики и страниц ошибок — если проверяешь именно
  это, ставь `DEBUG=False` на время.
